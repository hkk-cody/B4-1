# 6. 자원 측정·로그·cron·리포트

[이전](05-bash-and-monitor.md) · [목차](../README.md) · [다음: 문제 해결](07-troubleshooting.md)

**목표:** 로그 한 줄의 의미를 설명하고, 자동 실행과 보존 정책을 직접 확인한다.

## 6.1 어떤 자원을 측정하는가?

| 자원 | 뜻 | 이 코드의 측정 방식 |
| --- | --- | --- |
| CPU | 계산 작업을 수행하는 자원 | /proc/stat의 1초 전후 차이 |
| 메모리(MEM) | 실행 중인 데이터와 프로그램을 보관하는 자원 | MemTotal과 MemAvailable |
| 디스크(DISK) | 파일을 지속적으로 저장하는 공간 | 루트 파티션 df의 Used % |

**이 값은 앱 하나의 점유율이 아니라 VM의 시스템 전체 사용률이다.** 로그의 PID는 발견한 앱의 번호이며 CPU/MEM 숫자가 그 PID만의 수치라는 뜻은 아니다.

현재 CPU 계산에서 idle과 iowait는 유휴 쪽으로 묶는다. 누적 시간의 증가량을 다음처럼 비교한다.

```text
CPU 사용률 = 100 × (전체 증가량 - 유휴 증가량) / 전체 증가량
```

예를 들어 전체가 100 증가하는 동안 유휴가 75 증가했다면 25%다. 여러 CPU 코어의 합계로 정규화하므로 코어가 많은 VM에서 앱이 코어 하나를 바쁘게 써도 전체 사용률은 낮게 보일 수 있다. 메모리는 다음과 같다.

```text
MEM 사용률 = 100 × (MemTotal - MemAvailable) / MemTotal
```

사용 가능한 메모리가 8GB 중 6GB라면 사용률은 25%다. MemAvailable은 단순히 완전히 비어 있는 메모리만 뜻하지 않으며 재활용 가능한 캐시 등을 고려한 추정값이다.

```bash
grep -E '^(MemTotal|MemAvailable):' /proc/meminfo
df -P /
```

VM에서 읽기만 하는 명령이다. `/`는 루트 파티션을 대상으로 하라는 뜻이다. OrbStack의 표시 방식에 따라 보이는 가상 디스크 크기를 Mac의 실제 남은 공간과 같은 의미로 해석하면 안 된다.

## 6.2 실패와 경고의 차이

| 상황 | 현재 동작 | 정상 측정 로그 |
| --- | --- | --- |
| 앱 프로세스 없음 | FAIL, 종료 코드 1 | 추가하지 않음 |
| 지정 포트 LISTEN 없음 | FAIL, 종료 코드 1 | 추가하지 않음 |
| 자원 값을 수집하지 못함 | 실패 종료 | 추가하지 않음 |
| UFW 비활성 | WARNING 후 계속 | 기록 |
| 방화벽 조회 권한·명령 문제 | 조회 불가 WARNING 후 계속 | 기록. 조회 문제는 고쳐야 함 |
| CPU > 20 / MEM > 10 / DISK > 80 | WARNING 후 계속 | 기록 |
| 값이 기준과 같음 | 임계값 경고 없음 | 기록 |
| 다른 관제가 실행 중 | INFO로 이번 실행 건너뜀 | 이번 실행은 추가하지 않음 |

20과 20.1은 다르다. 기준이 `>`이므로 CPU 20.0%는 경고하지 않고 20.1%는 경고한다. 경고가 정상 기능이라고 해서 실제 운영의 높은 사용률을 무시하라는 뜻은 아니다. 이번 실습에서는 요구한 조건 분기가 작동하는지 확인한다.

## 6.3 로그 한 줄 읽기

```text
[2026-09-06 22:05:03] PID:4734 CPU:2.9% MEM:12.8% DISK_USED:2%
```

- 대괄호: 측정 결과를 기록한 시각
- PID: 실행 중인 앱으로 찾은 프로세스 번호
- CPU/MEM/DISK_USED: VM 전체 자원 사용률

앱이 재시작되면 PID가 바뀔 수 있다. 시각은 VM의 시간대를 따른다. 시각이 예상과 다르면 `date`나 `timedatectl`로 확인한다.

```bash
sudo -u agent-admin tail -n 5 /var/log/agent-app/monitor.log
```

`tail -f`는 새로 붙는 줄을 계속 보여 준다. 관찰을 끝내려면 Ctrl+C를 누른다. 이것은 tail을 종료하는 것이며 다른 터미널의 앱을 끄는 것은 아니다.

## 6.4 로그를 왜 회전시키는가?

매분 한 줄이라도 계속 쌓으면 파일은 끝없이 커진다. 로그 회전은 오래된 내용을 따로 보관하고 현재 파일을 작게 유지하는 방법이다.

```text
회전 전                  회전 후
monitor.log     ───────→ monitor.log.1
monitor.log.1   ───────→ monitor.log.2
       ...                        ...
monitor.log.8   ───────→ monitor.log.9
monitor.log.9   ───────→ 삭제
                         monitor.log ← 새 줄 기록
```

현재 코드의 기준:

- 한도는 10 × 1024 × 1024바이트, 즉 10MiB다. 과제의 10MB를 이 값으로 구현했다.
- **다음 로그 한 줄을 추가하면 한도를 넘는지** 먼저 계산한다.
- 현재 파일 하나와 회전본 9개로 총 10개를 유지한다.
- `.10` 이후처럼 이전 구현이 남긴 숫자 회전본도 정리한다.
- 직접 기록을 누적해 만든 정상 로그를 기준으로 한도 내 유지한다. 외부에서 이미 과도하게 큰 파일을 넣었다고 그 파일 내용을 잘라 복구하는 기능은 아니다.

`flock`은 한 번에 한 실행만 잠금을 잡게 한다. 수동 실행과 cron이 겹쳐 동시에 파일 이름을 바꾸는 일을 방지한다. 잠금 파일 `.monitor.lock`은 로그 회전본 수에 포함되는 측정 로그가 아니다.

회전 실험을 운영 로그에 직접 큰 파일을 채워 넣어서 하지 않는다. [test_monitor.sh](../../tests/test_monitor.sh)는 임시 디렉토리에서 10MiB 파일을 만들어 검증한 뒤 제거한다.

## 6.5 cron과 crontab

cron은 시간에 맞춰 명령을 실행하는 서비스이고 crontab은 실행 일정표다. **사용자마다 일정표가 따로 있다.** 이 과제의 실행자는 agent-admin이다.

```text
분  시  일  월  요일   실행할 명령
*   *   *   *   *      /home/agent-admin/agent-app/bin/monitor.sh
```

별표는 해당 칸의 모든 값을 의미한다. 다섯 칸이 모두 별표면 매분 실행이다.

확인:

```bash
sudo -u agent-admin crontab -l
sudo systemctl is-active cron
```

편집해야 할 경우에는 `sudo -u agent-admin crontab -e`를 사용한다. `setup.sh`가 이미 등록했으면 같은 항목을 다시 추가하지 않는다. 편집기 선택이 나오면 익숙한 편집기를 고르고, nano를 사용한다면 Ctrl+O → Enter로 저장, Ctrl+X로 종료한다. `crontab -r`은 일정표 전체 삭제이므로 목록 확인용으로 쓰지 않는다.

등록한 실제 줄:

```cron
* * * * * /home/agent-admin/agent-app/bin/monitor.sh >/dev/null 2>&1
```

`>/dev/null 2>&1`은 화면 출력을 버리는 부분이다. `monitor.log`는 스크립트 안에서 따로 기록한다. 실패 이유를 보고 싶으면 같은 계정으로 수동 실행해서 출력과 종료 코드를 확인한다.

## 6.6 터미널에서는 되는데 cron에서는 안 되는 이유

cron은 사용자가 열어 둔 터미널을 그대로 재사용하지 않는다. 환경 변수·PATH·현재 디렉토리가 다를 수 있다. 일반 로그인 셸처럼 `/etc/profile.d`를 자동으로 읽는다고 가정하면 안 된다.

현재 `monitor.sh`는 필요한 PATH, 로그 경로, 포트 기본값을 스스로 준비한다. 프로세스 패턴 환경 변수를 따로 등록할 필요도 없다. 다만 앱이 꺼져 있으면 cron이 실행되어도 정상 로그는 생기지 않는다.

**로그가 증가하지 않을 때 확인 순서:** 앱 → 수동 관제 → 파일 쓰기 권한 → agent-admin crontab → cron 서비스 → cron 실행 기록.

## 작은 실습: 자동 실행 증명하기

앱을 켠 뒤, 관제를 수동 실행하지 않는 1~2분 구간을 만든다.

```bash
date
sudo -u agent-admin wc -l /var/log/agent-app/monitor.log
sudo -u agent-admin tail -n 3 /var/log/agent-app/monitor.log
```

1~2분 뒤 똑같이 확인하고, `sudo journalctl -u cron --since '5 minutes ago' --no-pager`와 대조한다. 파일이 회전했다면 줄 수만 보지 말고 새 시각의 줄과 회전본을 본다.

[실제 이전 기록](../evidence/cron-before.txt)과 [이후 기록](../evidence/cron-after.txt)에서는 22:04:03의 6줄이 22:05:24에 7줄로 증가했다. 22:05:01의 cron 실행이 22:05:03의 로그를 남겼다.

## 6.7 보너스 과제에 대하여
 
원본 과제에는 `report.sh`로 통계 리포트를 만드는 보너스 1과, “7일 지난 로그 압축·30일 지난 아카이브 삭제”의 보너스 2가 있다. 이 과제에서는 **필수 과제에 집중하기 위해 보너스 1·2를 모두 수행하지 않는 것**으로 정리했다. 필수인 크기 기반 10MB 로그 회전은 `monitor.sh` 안에 온전히 구현되어 있다.
